Proposed issue title: **Add a governed early-review override lifecycle to the evidence CLI**

Exact issue body:

```markdown
## Problem Statement

Maintainers sometimes have evidence that waiting for the ordinary third occurrence would make coordinated fixes more costly, but they lack a compiled, local-first workflow for requesting an earlier review without weakening the decision contract. A valid early-review override must present why waiting is worse, the evidence references that bear that claim, and a bounded review appetite as one exact proposal. Human acceptance must attach to that exact proposal rather than to a paraphrase, a later revision, or an inferred intent.

The workflow must also remain safe under concurrent edits, retries, interruption, mixed public and private evidence, and stewardship across repositories. Today, the active design's direct input shape names only the reason and review appetite. It does not define how evidence references enter the prepared proposal, so it cannot yet satisfy the foundational contract and must not be implemented or published as complete.

## Solution

Provide a compiled CLI workflow that, once the active design is amended, prepares all three required parts of an early-review proposal, renders the exact proposal for review without writing evidence, and records a human decision only when the accepted proposal, expected case revision, and event identity still match.

The workflow will use the accepted per-event case evidence model, preserve a stable event identity across safe retries, reject stale or conflicting attempts without writes, derive privacy from the evidence and repository context, let private status dominate mixed inputs, and render a privacy-safe receipt. It will support resumption after interruption without relying on process memory and will keep stewardship explicit when evidence spans repositories. It will delegate any resulting implementation work outside the reuse-review lifecycle and return later for verification.

## User Stories

**Proposal preparation**

1. As a maintainer, I want to state why waiting for ordinary review readiness is worse, so that an early-review request has a concrete urgency claim.
2. As a maintainer, I want to attach the evidence references that bear the urgency claim, so that a reviewer can assess the request against identified evidence rather than assertion alone.
3. As a reviewer, I want the proposal to state a bounded review appetite, so that accepting an override does not authorize an open-ended architecture review.

**Preview**

4. As a maintainer, I want to preview the complete canonical proposal before recording anything, so that I can catch omissions or unintended wording without changing case evidence.
5. As an unattended implementation agent, I want a deterministic preview that can be handed to a human unchanged, so that approval is sought for the same proposal the CLI prepared.
6. As a private-repository steward, I want preview output to respect derived privacy, so that preparing a proposal cannot leak private repository identities or evidence.

**Exact approval**

7. As a reviewer, I want my decision bound to the exact proposal I saw, so that later changes cannot inherit my approval.
8. As a maintainer, I want any proposal change after preview to require a fresh human decision, so that acceptance cannot silently drift.
9. As an unattended implementation agent, I want the record operation to prove that the supplied decision refers to the prepared proposal, so that I never infer or manufacture human acceptance.

**Expected revision**

10. As an operator, I want recording to require the case revision I reviewed, so that concurrent case changes cannot be overwritten or ignored.
11. As an unattended implementation agent, I want a revision mismatch reported before any write, so that I can stop and return the changed state to a human.
12. As a reviewer, I want the accepted decision rejected when its expected revision is absent or malformed, so that ambiguous concurrency checks cannot degrade into best-effort writes.

**Event identity**

13. As an operator, I want each proposed decision event to have an exact identity before recording, so that I can safely correlate attempts and receipts.
14. As an unattended implementation agent, I want to reuse the same event identity when retrying the same accepted proposal, so that an uncertain result does not create duplicates.
15. As a maintainer, I want reuse of an event identity for different content to be rejected, so that event identity remains trustworthy.

**Event recording**

16. As a maintainer, I want a successful decision recorded as its own case event, so that the evidence history remains append-only and inspectable.
17. As a reviewer, I want the recorded event to preserve the exact proposal, decision, expected revision, event identity, and derived privacy outcome, so that the decision can later be verified.
18. As an unattended implementation agent, I want recording to stop at the bounded decision event, so that an accepted override does not itself perform the delegated refactor or implementation.

**Idempotent retry**

19. As an operator resuming an uncertain command, I want to repeat the identical recording request without creating another event, so that retries are operationally safe.
20. As an unattended implementation agent, I want a successful replay to identify the already-recorded event, so that I can distinguish recovery from a new decision.
21. As a maintainer, I want a retry with the same identity but different proposal or decision data refused, so that idempotence cannot conceal a conflict.

**Stale revision refusal**

22. As an operator, I want a stale expected revision to produce a refusal with exit status 3, so that automation can distinguish a governed refusal from success.
23. As a maintainer, I want stale-revision refusal to leave all case evidence byte-for-byte unchanged, so that concurrency protection is real rather than advisory.
24. As an unattended implementation agent, I want stale-revision output to identify the mismatch without exposing private evidence, so that I can route the case back for review safely.

**Privacy derivation**

25. As a private-repository steward, I want privacy derived from the repositories and evidence involved, so that callers cannot accidentally under-classify a proposal.
26. As a reviewer, I want the preview and receipt to use the same derived privacy result, so that approval is not obtained from a less restrictive representation than the record.
27. As an operator, I want the CLI to explain a safe, high-level privacy outcome, so that I can understand routing without receiving protected identities or source material.

**Private dominance**

28. As a private-repository steward, I want any private constituent to make the complete proposal, event, and receipt private, so that mixed evidence cannot leak through a public constituent.
29. As a maintainer coordinating evidence across repositories, I want private status to dominate regardless of repository ordering, so that classification is deterministic.
30. As an operator retrying an event, I want the original private classification preserved or strengthened but never downgraded, so that retries cannot become a privacy bypass.

**Receipt rendering**

31. As a maintainer, I want a successful command to render the event identity, recorded outcome, and resulting revision, so that I have a useful completion receipt.
32. As an unattended implementation agent, I want retry receipts to make clear that an existing event was reused, so that I do not report a duplicate as a new decision.
33. As a private-repository steward, I want receipts to omit or redact protected repository and evidence details, so that operational logs remain safe.

**Interruption and resumption**

34. As an operator interrupted after preview but before approval, I want to regenerate and compare the exact proposal before proceeding, so that process memory is not treated as authorization.
35. As an operator interrupted after the write but before seeing the receipt, I want to resume by retrying the same event identity, so that I can recover the result without duplication.
36. As an unattended implementation agent restarted in a new process, I want all recovery decisions derived from durable local state and explicit inputs, so that session continuity is not required for correctness.

**Cross-repository stewardship**

37. As a maintainer, I want the target case and participating repositories selected explicitly, so that evidence is never gathered merely because a repository is nearby.
38. As a private-repository steward, I want a cross-repository proposal routed according to its private participants without copying their identities into public state, so that stewardship boundaries are preserved.
39. As an operator, I want the workflow to refuse unmarked or unenrolled repositories, so that cross-repository convenience cannot expand the authorized evidence surface.

**Testing at the public CLI seam**

40. As a maintainer, I want the compiled CLI exercised end to end against temporary local state, so that the accepted behavior is proven at the interface people and agents actually use.
41. As an unattended implementation agent, I want tests to invoke only supported public commands and inspect public outputs and durable effects, so that internal restructuring does not invalidate behavioral evidence.
42. As a reviewer, I want exact-approval, revision, identity, privacy, and retry invariants proven together through the CLI, so that lower-level unit success cannot mask a broken workflow.

**Unsafe failure**

43. As an operator, I want incomplete, malformed, or internally inconsistent proposal inputs rejected before any write, so that unsafe requests fail closed.
44. As a private-repository steward, I want unresolved privacy or repository stewardship state to block recording, so that uncertainty cannot default to public handling.
45. As a maintainer, I want storage failures to avoid partial visible events and report that success was not established, so that recovery can use the idempotent protocol safely.

**Refusal exit status 3**

46. As an unattended implementation agent, I want all governed refusals to exit with status 3, so that automation can route them for human attention without treating them as crashes.
47. As an operator, I want each refusal to render a specific, actionable reason, so that I can distinguish stale revision, identity conflict, incomplete proposal, and unsafe privacy state.
48. As a reviewer, I want refusal tests to assert status 3, refusal output, and write-free behavior together, so that the refusal contract is complete.

**Documentation**

49. As a maintainer, I want documentation for preparation, preview, exact approval, recording, retry, and verification, so that I can operate the whole lifecycle deliberately.
50. As an unattended implementation agent, I want documentation to identify required inputs and stop points without implying that I may accept on a human's behalf, so that the authority boundary remains explicit.
51. As a private-repository steward, I want documentation for privacy dominance, cross-repository routing, interruption, and safe resumption, so that exceptional operations do not become leak paths.

## Implementation Decisions

- Use one compiled public CLI workflow as the primary consumer interface and acceptance seam. Do not introduce a lower-level public API solely to make the feature easier to test.
- Preserve the active design's decision to use direct inputs for the reason and bounded review appetite, represented by `--reason` and `--review-appetite`.
- Do not implement or publish the workflow until the active design is amended to define an explicit evidence-reference input. The prepared proposal must contain the reason waiting is worse, one or more evidence references bearing that claim, and the bounded review appetite.
- Canonicalize the complete prepared proposal and bind preview, human acceptance, recording, and retry to that exact content. Any material change requires a new approval.
- Make preview write-free. Preview must expose enough privacy-safe information for exact human review without creating a case event or advancing a revision.
- Require the caller to supply the expected case revision when recording. Compare it before writing and refuse stale, missing, or malformed values.
- Establish an exact event identity before the first recording attempt. Replaying the same identity with the same accepted content returns the existing outcome; replaying it with different content refuses.
- Record a successful decision as one immutable per-event case evidence record. Advance the case revision only once, even when the command is retried.
- Keep reuse-review ownership bounded to proposal evidence, readiness override, human decision, receipt, and later verification. Produce a bounded implementation brief and delegate implementation work to the ordinary engineering workflow.
- Derive privacy from every repository and evidence item participating in the proposal. A private participant dominates the complete proposal, recorded event, preview, and receipt; caller preference cannot weaken it.
- Keep repository selection explicit and limited to enrolled or otherwise authorized repositories. Do not discover participants by scanning a configured root.
- Render completion and replay receipts with the event identity, outcome, and resulting revision while omitting protected repository identities, paths, source, and evidence from public output.
- Support interruption by relying on explicit proposal content, expected revision, event identity, and durable local event state rather than hidden session state.
- Validate the complete request and its privacy and concurrency conditions before writing. A refusal must make no state change; a failed write must not expose a partial valid event.
- Document the authority handoff: preview precedes human acceptance, acceptance applies only to the exact proposal, recording does not authorize implementation, and verification follows delegated implementation.

## Testing Decisions

- Treat the compiled public CLI as the primary test seam. Tests should assert externally visible output, exit status, and durable local state, not private functions or internal representation.
- Use end-to-end CLI fixtures with temporary repositories and case stores. Prior art is the repository's existing case-command integration suite and its revision and event-recording scenarios.
- Prove proposal preparation rejects omission of any foundational component: the reason waiting is worse, evidence references, or bounded review appetite.
- Prove preview renders the complete exact proposal, derives privacy, remains write-free, and is stable enough for exact approval handoff.
- Prove a decision records only when the accepted proposal identity and expected revision match. Mutating any proposal component after approval must refuse.
- Prove fresh event recording, identical retry before receipt recovery, identical retry after restart, and conflicting identity reuse as separate cases.
- Prove stale, missing, and malformed expected revisions refuse with exit status 3, actionable output, and unchanged state.
- Prove each governed refusal class with the three-part contract: refusal output, exit status 3, and write-free behavior.
- Prove mixed public and private evidence in both repository orderings. The complete proposal, event, preview, and receipt must remain private-safe whenever any participant is private.
- Prove cross-repository operations accept only explicit authorized participants and never render protected identities or paths into public state.
- Prove interruption after preview and interruption after recording but before receipt. Resumption must either regenerate the exact proposal or return the already-recorded event without duplication.
- Prove unsafe input, unresolved privacy, and simulated storage failure do not leave a partial valid event or advance the case revision.
- Exercise compiled help and user documentation examples once the evidence-reference input is accepted, so that the documented lifecycle stays aligned with the public command.

## Out of Scope

- Amending the foundational exact-proposal contract through this PRD.
- Inventing the evidence-reference flag name, cardinality, or syntax before the active design is explicitly amended and accepted.
- Changing the ordinary third-occurrence review-readiness rule.
- Treating an early-review override as extraction authority or as permission to implement a refactor inside the reuse-review capability.
- Clone detection, similarity scanning, general architecture auditing, or scanning unmarked repositories.
- Automatic end-of-session capture, automatic refactoring hooks, clean or no-candidate evidence records, or unattended human-decision substitution.
- A hosted service, daemon, MCP server, sensor-plugin platform, or central portfolio repository.
- A shared lifecycle kernel with another governance tool without a third independent consumer creating real pressure.
- New compatibility promises, storage schemas, or verification commands beyond those already accepted and implemented.

## Further Notes

- The ratified test seam is the compiled public CLI; no additional seam confirmation is needed.
- The earlier design discussion established the semantic values for reason and review appetite, but it was not a prototype. Its illustrative schema is therefore expressed as prose rather than copied as a snippet.
- The sought consumer effect is a safe, resumable way to request bounded review before ordinary readiness when waiting is demonstrably worse.
- The live blocker is not storage or command compilation; it is the missing accepted route for evidence references in the active two-field direct-input design.
- The evidence bearing this proposal is the foundational exact-proposal contract, the accepted per-event case evidence decision, the active CLI design, and the accepted capability coverage matrix.
- The narrowest useful scope is proposal preparation, write-free preview, exact human decision recording, safe retry, privacy-safe receipt, and documentation through the compiled CLI.
- Publication and implementation must remain parked until the active design defines the evidence-reference input and a human accepts that amendment. If the amended design cannot preserve exact approval, write-free refusal, private dominance, and idempotent retry at the public CLI seam, this proposal is falsified and should be narrowed or parked.
- This issue is a coordinating parent and is not independently grabbable implementation work.
```
