Proposed issue title: Add a governed early-review override to the evidence CLI

Exact issue body:

## Problem Statement

Maintainers sometimes need a bounded human review before a case reaches ordinary third-occurrence review readiness because the cost of waiting has become greater than the cost of reviewing early. The evidence CLI does not yet provide a complete, compiled workflow for preparing that exception, showing exactly what would be approved, binding a human decision to the exact prepared proposal, and recording the result safely.

An early-review override is a governed exception, not a shortcut around evidence. The foundational decision contract requires each prepared proposal to contain why waiting is worse, the evidence references bearing that claim, and a bounded review appetite. The active direct-flag design currently represents only the reason and review appetite. It therefore cannot yet express a conforming proposal. Publishing or implementing the two-field form would allow a lower-level design to weaken a foundational contract.

Without one public CLI workflow, an unattended implementation agent or a maintainer could also approve a stale case revision, duplicate an event during retry, confuse two attempts, expose private repository information in a receipt, or leave interrupted work in an ambiguous state. Cross-repository evidence makes these risks sharper because the most restrictive privacy classification must govern the whole decision.

## Solution

Provide a local-first, compiled CLI workflow that prepares an exact early-review proposal, previews its complete approval-bearing representation, accepts a human decision only for that exact representation and expected case revision, and records one immutable event with a stable event identity. The proposal must contain all three foundational elements: a reason that explains why waiting is worse, evidence references bearing that claim, and a bounded review appetite.

The workflow will make retries idempotent, refuse stale revisions without writing, derive privacy from the referenced evidence, apply private dominance whenever any contributing evidence is private, and render a useful receipt without disclosing protected repository identities, paths, source, or evidence. Its persisted event and receipt will allow an operator to determine whether interrupted work can be resumed, replayed, or must be prepared again.

The active design must first be amended and accepted to add a bounded evidence-reference input to the direct-flag proposal shape while retaining the already accepted reason and review-appetite inputs. This PRD is a conditional draft until that smallest amendment is accepted; it is not authority to implement or publish the incomplete two-field shape.

## Implementation Decisions

- The feature will be exposed through the compiled public CLI and will remain local-first. It will not require a hosted component, daemon, central portfolio service, or plugin platform.
- A prepared proposal is one exact approval-bearing value with three mandatory semantic elements: why waiting is worse, the evidence references bearing that claim, and a bounded review appetite. Empty, missing, or malformed elements are refused.
- The active direct-flag design retains its reason and review-appetite inputs, but it is incomplete until an accepted design amendment adds a bounded evidence-reference input. No evidence-reference flag name, cardinality syntax, or compatibility promise is selected by this PRD.
- Preview renders the complete proposal that the human is being asked to accept. The acceptance mechanism binds to that exact proposal rather than merely to the case or command invocation.
- Recording requires the expected case revision and a stable event identity. The expected revision is checked immediately before the durable write.
- Each accepted override is recorded as its own immutable case event, consistent with the accepted per-event evidence decision. A successful recording advances case state exactly once.
- Retrying with the same event identity and identical approval-bearing content returns the existing outcome without a second write. Reusing an event identity with different content is a refusal.
- A stale expected revision, absent exact approval, changed proposal, invalid evidence reference, uncertain privacy classification, or event-identity conflict is a governed refusal. Governed refusals exit with status 3 and perform no case write.
- Validation and derivation happen before the commit boundary. Durable creation is atomic from the CLI consumer's perspective; after an ambiguous interruption, the caller resumes by querying or retrying with the same event identity.
- Privacy is derived from the referenced evidence and cannot be weakened by a caller-provided assertion. Private classification dominates when any contributing evidence is private or when classification cannot be established safely.
- Preview, refusal output, success receipts, and replay receipts render only disclosure-safe information. They must not expose private repository names, paths, source, or evidence into public state.
- Cross-repository references are limited to explicitly enrolled repositories within the operator's stewardship. Configured-root proximity alone grants no authority to inspect a repository.
- The recorded override establishes bounded review authority only. It does not establish extraction authority, perform a refactor, or delegate implementation inside the reuse lifecycle.
- Documentation is delivered with the compiled behavior and covers proposal requirements, exact approval, concurrency, retries, privacy, receipts, exit status 3, and recovery after interruption.

## Testing Decisions

- Acceptance tests use the compiled public CLI as the highest seam. They assert command input, rendered standard output and error output, process exit status, and durable case state. Tests do not couple to internal helper calls or storage implementation details.
- The existing case CLI integration style is the prior art: invoke the real binary against isolated local case state and inspect only consumer-visible results and persisted events.
- Proposal tests cover all three required elements, deterministic complete preview, missing and malformed inputs, and proof that changing any approval-bearing element invalidates prior acceptance.
- Exact-approval tests prove that the shown proposal can be recorded, an unseen or changed proposal cannot, and an approval for one case revision or event identity cannot authorize another.
- Concurrency tests prove success at the expected revision, write-free refusal at a stale revision, and refusal when the revision is missing or malformed.
- Event tests prove unique recording, stable event identity in receipts, one revision advance, immutable history, and conflict when an identity is reused with different content.
- Retry tests simulate an interrupted or lost response and prove that replay with identical inputs returns the recorded outcome without a duplicate event or additional revision advance.
- Privacy tests cover public-only evidence, private-only evidence, mixed public and private evidence, order independence, a newly added private reference, unavailable provenance, and disclosure-safe rendering.
- Cross-repository tests prove that explicitly enrolled evidence can participate, unmarked repositories are not scanned, and private identities never enter public output or state.
- Unsafe-failure tests cover validation failure, missing evidence, privacy uncertainty, write failure before commit, and ambiguous interruption. Each test asserts output, exit status, and the precise presence or absence of durable writes together.
- Refusal tests assert status 3, a useful refusal message, and write-free behavior for every governed refusal class. Operational faults remain distinguishable from governed refusal and success.
- Documentation checks verify that the public command guidance matches the compiled behavior and does not promise an unaccepted schema, compatibility surface, or automatic workflow.

## Out of Scope

- Changing the foundational exact-proposal contract or treating a two-field proposal as sufficient.
- Selecting and accepting the required active-design amendment; that human authority must occur before this PRD can be published.
- Changing ordinary third-occurrence readiness or treating an override as extraction authority.
- Discovering evidence, scanning unmarked repositories, performing a general architecture audit, or building a clone detector.
- Implementing refactors, delegating implementation within the reuse-review capability, or replacing the ordinary engineering workflow.
- Automatic end-of-session capture, refactoring hooks, clean or no-candidate evidence records, or unattended human-decision inference.
- A hosted service, daemon, central portfolio repository, sensor-plugin platform, or new cross-product lifecycle kernel.
- Public disclosure of private repository identities, paths, source, evidence, or provenance.
- New file-format guarantees, command aliases, migration rules, or compatibility promises beyond separately accepted and implemented behavior.

## Further Notes

The governing evidence is the foundational requirement that an early-review proposal contain all three approval-bearing elements, the accepted per-event case evidence decision, the active design's current two-direct-flag summary, and the conversation's request to carry that two-field shape forward. The last two conflict with the first.

The smallest conforming authority change is an accepted amendment to the active design adding bounded evidence-reference input to the direct-flag shape while retaining the reason and review-appetite inputs. The foundational principle does not need amendment. Until that design amendment is accepted, implementation and tracker publication are parked.

This proposal should also be parked or revisited if the public CLI cannot bind acceptance to the exact previewed proposal, cannot make stale or policy refusal write-free, cannot preserve private dominance across repositories, or cannot make ambiguous interruption safely recoverable through stable event identity and idempotent retry.
