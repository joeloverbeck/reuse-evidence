Proposed issue title: Coordinate a governed compiled early-review override

Exact issue body:

## Problem Statement

Maintainers sometimes have evidence that waiting for the ordinary review-readiness threshold is more costly than conducting one bounded review now. The local-first evidence CLI cannot yet prepare, present, approve, record, retry, or resume that exception as one governed workflow. As a result, an operator or unattended implementation agent could act on an incomplete rationale, an approval could drift away from the proposal a human actually saw, a retry could duplicate a decision event, or a receipt could expose private repository information.

The live bottleneck is not discovering more candidate work; it is preserving an exact, reviewable chain from a justified early-review proposal through a human decision and an immutable event, while keeping failures safe and public receipts privacy-preserving. The governing evidence is the foundational requirement that every proposal contain why waiting is worse, the evidence references bearing that claim, and a bounded review appetite, together with the active design's preference for a short direct-flag CLI.

## Solution

Add a compiled early-review override workflow to the local-first evidence CLI. The workflow prepares an exact proposal containing all three governed elements, previews the proposal without recording an approval, accepts only a human decision bound to that exact proposal and expected case revision, records one identifiable immutable event, and renders a privacy-safe receipt. A repeated attempt with the same identity is idempotent; an attempt against a stale revision, an altered proposal, incomplete governance inputs, or unsafe privacy state refuses with exit status 3 and performs no writes.

Keep the interface direct-flag based and the implementation bounded to this exception workflow. The reason input states why waiting is worse, the review-appetite input states the bounded review being authorized, and an explicit evidence-reference input carries the evidence bearing the reason. This is the narrowest shape that satisfies the foundational three-part proposal contract. The issue coordinates separately implementable work and is not independently grabbable.

## User Stories

**Proposal preparation**

1. As a maintainer, I want to prepare an early-review proposal that states why waiting is worse, so that the exception has a decision-bearing rationale.
2. As an unattended implementation agent, I want proposal preparation to require evidence references, so that I cannot infer or silently omit the evidence bearing the rationale.
3. As a reviewer, I want every prepared proposal to state a bounded review appetite, so that the requested exception has an explicit limit.

**Preview**

4. As a maintainer, I want to preview the complete prepared proposal before asking for approval, so that I can catch omissions without creating a decision event.
5. As a private-repository steward, I want preview output to apply the proposal's privacy rules, so that checking it cannot leak protected repository identity or evidence.
6. As an operator resuming interrupted work, I want the preview to reproduce the exact proposal that remains pending, so that I know what can still be approved.

**Exact approval**

7. As a reviewer, I want my approval bound to the exact proposal I was shown, so that later edits cannot inherit my decision.
8. As a maintainer, I want any change to the rationale, evidence references, or review appetite to require a new approval, so that acceptance never floats across proposal versions.
9. As an unattended implementation agent, I want the CLI to reject an approval that cannot be matched to the presented proposal, so that automation cannot manufacture human authority.

**Expected revision**

10. As a maintainer, I want to submit the case revision I reviewed, so that the decision is applied only to the expected state.
11. As an operator resuming interrupted work, I want the current revision reported after a mismatch, so that I can refresh deliberately rather than guess.
12. As a reviewer, I want concurrent case changes detected before recording, so that my decision cannot overwrite or ignore newer evidence.

**Event identity**

13. As an unattended implementation agent, I want each intended decision event to have a stable identity, so that retry behavior is deterministic.
14. As a maintainer, I want the event identity represented in the success receipt, so that I can correlate the command result with the recorded event.
15. As an operator resuming interrupted work, I want to reuse the original event identity, so that resumption does not create a second logical decision.

**Event recording**

16. As a maintainer, I want an accepted early-review decision recorded as an immutable event, so that the case history preserves what happened.
17. As a reviewer, I want the event to preserve the accepted proposal and decision relationship, so that future readers can audit the authority chain.
18. As a private-repository steward, I want recording to retain the evidence needed for local verification without copying protected details into public state, so that auditability and confidentiality both survive.

**Idempotent retry**

19. As an operator resuming interrupted work, I want retrying an already-recorded event to return the prior success rather than append another event, so that recovery is safe.
20. As an unattended implementation agent, I want a retry with the same identity but different decision-bearing content refused, so that identity reuse cannot overwrite history.
21. As a maintainer, I want an idempotent retry receipt to identify the existing event, so that I can distinguish recovery from a new write.

**Stale revision refusal**

22. As a maintainer, I want a stale expected revision to be refused before any write, so that concurrent updates remain intact.
23. As a reviewer, I want stale-state refusal to invalidate the attempted approval path, so that a decision cannot be replayed after the case changes.
24. As an unattended implementation agent, I want stale revision refusal to be machine-detectable, so that automation stops instead of retrying with guessed authority.

**Privacy derivation**

25. As a private-repository steward, I want proposal and receipt privacy derived from the repositories and evidence involved, so that callers cannot downgrade protection by assertion.
26. As a maintainer, I want the derived privacy result available to the workflow before recording, so that unsafe output is caught before state changes.
27. As a reviewer, I want the preview to communicate the derived privacy class without exposing the protected inputs that caused it, so that I can understand the handling obligation safely.

**Private dominance**

28. As a private-repository steward, I want any private participating evidence to make the combined proposal private, so that mixed public and private inputs cannot weaken protection.
29. As a maintainer, I want private dominance to apply consistently to previews, events, and receipts, so that no later rendering step reclassifies the same decision as public.
30. As an unattended implementation agent, I want ambiguous or conflicting privacy inputs to fail closed, so that uncertainty never becomes accidental disclosure.

**Receipt rendering**

31. As a maintainer, I want a successful receipt to report the decision outcome, event identity, resulting revision, and whether the operation recorded or reused an event, so that the result is operationally useful.
32. As a reviewer, I want the receipt to demonstrate that the accepted decision corresponds to the exact prepared proposal without reproducing protected evidence, so that the result is auditable.
33. As a private-repository steward, I want public-facing receipts to redact private identities, paths, source, and evidence, so that cross-boundary reporting remains safe.

**Interruption and resumption**

34. As an operator resuming interrupted work, I want to determine whether recording completed before the interruption, so that I can choose preview, retry, or stop safely.
35. As a maintainer, I want resumption to use persisted proposal, revision, and event identity rather than reconstructed guesses, so that the resumed command preserves exactness.
36. As an unattended implementation agent, I want an interruption before a durable event to leave no partial success claim, so that later automation does not treat incomplete work as accepted.

**Cross-repository stewardship**

37. As a maintainer, I want an early-review proposal to reference evidence from explicitly involved repositories, so that the scope of stewardship is clear.
38. As a private-repository steward, I want cross-repository output to omit protected repository identities and locations, so that one repository cannot disclose another.
39. As a reviewer, I want the decision receipt to distinguish the governed case from external evidence ownership without routing the external evidence into public state, so that responsibilities remain legible.

**Public CLI testing seam**

40. As a maintainer, I want the full workflow tested through the compiled public CLI, so that acceptance covers the interface users and agents actually invoke.
41. As an unattended implementation agent, I want tests to assert output bytes, exit status, and filesystem effects together, so that a superficially correct message cannot hide an unsafe write.
42. As a reviewer, I want preview, success, retry, stale refusal, privacy, and resumption exercised at one public seam, so that lower-level implementation details do not substitute for behavior proof.

**Unsafe failure**

43. As a private-repository steward, I want the command to fail closed when privacy cannot be derived safely, so that incomplete metadata cannot become disclosure.
44. As a maintainer, I want malformed or incomplete proposals rejected before recording, so that no partial decision enters case history.
45. As an operator resuming interrupted work, I want ambiguous persistence outcomes reported as unsafe rather than guessed successful, so that recovery requires evidence.

**Refusal exit 3**

46. As an unattended implementation agent, I want every governed refusal to exit with status 3, so that automation can distinguish refusal from success and unrelated failure.
47. As a maintainer, I want exit status 3 paired with an actionable refusal message, so that I can correct the proposal or refresh state deliberately.
48. As a reviewer, I want tests to prove that exit status 3 refusals are write-free, so that the refusal contract covers effects as well as signaling.

**Documentation**

49. As a maintainer, I want documentation for preparing, previewing, approving, retrying, and resuming an early-review proposal, so that the governed path can be followed without reverse-engineering it.
50. As an unattended implementation agent, I want the CLI contract and refusal status documented, so that automation can invoke the workflow predictably.
51. As a private-repository steward, I want documentation to explain privacy derivation, private dominance, and safe receipt rendering, so that operators understand the confidentiality boundary.

## Implementation Decisions

- The feature is a compiled CLI workflow over the existing case lifecycle, not a separate service or automation hook.
- The prepared proposal is one exact decision-bearing value containing a reason that explains why waiting is worse, one or more evidence references bearing that claim, and a bounded review appetite.
- The CLI remains direct-flag based. The reason and review-appetite flags retain their established meanings; the active design must add an explicit evidence-reference input before implementation can be authorized.
- Preview renders the complete proposal and its derived privacy treatment without recording a decision event.
- Human approval is bound to the exact previewed proposal. Any change to any of its three governed elements produces a different proposal requiring fresh acceptance.
- Recording requires the caller's expected case revision and refuses before writing if the current revision differs.
- Each logical decision event has a caller-reusable stable identity. A retry of the same identity and same decision-bearing content returns the existing result; conflicting content under that identity is refused.
- Successful recording appends one immutable case event and advances the case revision atomically from the caller's expected revision.
- Privacy is derived from the participating evidence and repository stewardship context rather than selected by the caller. Private input dominates mixed input, and ambiguity fails closed.
- Receipts expose only operationally necessary identifiers and outcomes. Public rendering never includes private repository identities, paths, source, or evidence.
- The workflow exposes enough persisted identity and revision information to distinguish completed recording from an unrecorded interruption and to resume by safe retry.
- The coordinating parent should be decomposed into bounded implementation children only after the authority conflict below is resolved; those children remain responsible for ordinary interface design, TDD, implementation, and review.

## Testing Decisions

- Use the compiled public CLI as the single primary acceptance seam. Tests assert external behavior rather than internal helpers or storage layout.
- For every refusal case, assert the exact observable message, exit status 3, and absence of filesystem writes together.
- Cover preparation requirements, write-free preview, exact-approval binding, expected-revision success, stale-revision refusal, event identity, immutable recording, idempotent retry, conflicting retry refusal, and interruption recovery.
- Cover privacy derivation, private dominance, mixed-repository stewardship, safe public receipts, and fail-closed behavior when privacy is missing, malformed, ambiguous, or conflicting.
- Exercise success receipts and replay receipts through the same CLI seam, including their event identity, resulting revision, and recorded-versus-reused outcome without coupling assertions to internal representation.
- Use the repository's existing compiled case-command integration tests as prior art for process invocation, output capture, exit-code assertions, and write-effect inspection.
- Prefer one coherent CLI journey with focused refusal cases over adding lower-level test seams unless a behavior cannot be observed through the public command.

## Out of Scope

- Changing the ordinary third-occurrence readiness rule or treating this override as extraction authority.
- Automatic approval, inferred human acceptance, or approval that survives a changed proposal.
- Automatic end-of-session capture, refactoring hooks, or implementation of the resulting reuse decision.
- Clone detection, broad architecture discovery, scanning unmarked repositories, or a hosted service, daemon, server, sensor platform, or central portfolio store.
- Publishing private repository identities, paths, source, or evidence in public events or receipts.
- Defining unrelated case commands, storage compatibility promises, or a shared lifecycle abstraction.
- Amending foundational principles or the accepted active design through this PRD.

## Further Notes

The human effect sought is a safe, bounded exception when waiting is demonstrably worse, without weakening exact human authority or private-evidence handling. This proposal conforms to the foundational three-part decision contract, immutable event recording, local-first operation, and the repository boundary between reuse decisions and ordinary implementation work.

Publication is blocked because the currently accepted active design names only the reason and review-appetite direct flags, while the foundational contract requires evidence references in the exact prepared proposal. The smallest authority amendment is an explicit human-accepted change to the active design adding evidence references to the direct-flag proposal shape. This PRD cannot make that amendment itself. The earlier illustrative two-field schema is not inlined because it came from design discussion rather than a prototype and omits the required third element.

Park this work if maintainers cannot provide a bounded real case where waiting is worse, or if safe privacy derivation and write-free refusal cannot be demonstrated at the compiled CLI seam. Falsify the proposal if exact approval cannot remain bound across preview, expected-revision recording, interruption, and idempotent retry.
