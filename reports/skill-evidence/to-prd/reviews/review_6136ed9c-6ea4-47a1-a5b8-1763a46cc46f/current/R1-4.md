Proposed issue title: **Add a governed early-review override command**

Exact issue body:

```markdown
## Problem Statement

Maintainers sometimes have evidence that waiting for the ordinary third-occurrence review threshold is already more costly than conducting one bounded review. The local-first evidence CLI has no compiled, resumable way to prepare that exceptional claim, show a human exactly what would be accepted, bind approval to that exact proposal, and record the decision without weakening the ordinary threshold. Ad hoc handling risks approval drift, stale writes, duplicate events, unsafe partial state, and disclosure of private repository information.

The live bottleneck is therefore not automatic review detection; it is a narrow, governed path for a human to authorize an early review from a proposal that contains why waiting is worse, the evidence references bearing that claim, and a bounded review appetite. Each invocation must carry its own evidence. This feature must remain subordinate to the foundational decision contract and the accepted per-event evidence model.

## Solution

Add a compiled early-review override workflow to the local-first CLI. It prepares an exact proposal containing all three required parts, renders that proposal for inspection, accepts a human decision only for the exact rendered proposal at an expected case revision, and records one immutable event with a stable event identity. Safe retries return the already-recorded result without duplicating the event, while stale, incomplete, conflicting, or unsafe attempts fail closed without writes.

Privacy is derived from the referenced evidence rather than trusted as an independent assertion. Private classification dominates mixed public/private inputs, and every output surface, durable record, and receipt must honor that classification. The workflow supports interruption and later resumption, including stewardship across enrolled repositories, while keeping implementation work outside the reuse-review lifecycle.

## Implementation Decisions

- Treat this issue as a coordinating parent for separately implementable command, persistence, privacy, receipt, test, and documentation work. The parent is not independently grabbable.
- Preserve the ordinary third-occurrence readiness rule. The new workflow is an explicit human-authorized override and does not itself discover, recommend, or approve early review.
- Represent a prepared proposal as one exact decision object containing why waiting is worse, one or more evidence references bearing that claim, and a bounded review appetite. Missing any part is a governed refusal.
- Keep the accepted direct-input style. The existing `--reason` and `--review-appetite` flags remain direct inputs, but the active design must first be amended to add an explicit evidence-reference input and ratify its spelling, multiplicity, and canonicalization. This PRD cannot make that amendment.
- Use one compiled workflow with preparation, privacy-safe preview, exact acceptance, and recording stages. Acceptance must bind to the complete prepared representation, not merely its two short text fields.
- Require an expected case revision when recording. Compare it at the write boundary and refuse stale state without producing an event.
- Require a stable event identity for recording and retry. An exact repeat returns the existing outcome; reuse of the identity with different decision content or context is refused.
- Record each accepted decision as one immutable per-event case record. Do not update an existing event in place and do not write clean or no-candidate evidence records.
- Make the write atomic from the public command's perspective: success means the complete event is durable, while any failure before that point leaves no partial event.
- Derive privacy from the referenced enrolled evidence under existing stewardship rules. Do not accept a caller-selected privacy downgrade; private evidence dominates mixed inputs.
- Render previews, errors, and receipts from privacy-safe projections. Public surfaces must not reveal private repository identities, paths, source, or evidence.
- Support interruption by allowing a prepared proposal to be reproduced and a recording attempt to be retried with the same expected revision and event identity. Do not treat interruption as acceptance.
- Resolve cross-repository evidence only across repositories explicitly enrolled for the case. Do not scan repositories merely because they share a configured root.
- After a decision is recorded, emit a bounded implementation brief and yield implementation to ordinary engineering workflows. This capability records readiness, decisions, and verification; it does not perform the refactor.

## Testing Decisions

- The acceptance seam is the compiled public CLI. Exercise it as a black box and assert arguments, standard output, standard error, exit status, and durable filesystem effects together.
- Good tests describe externally visible behavior rather than private function calls, internal type layout, or storage helper sequencing.
- Test the command workflow, immutable event recording, revision guard, retry identity, privacy derivation, private-dominant rendering, and receipt as one observable lifecycle wherever practical. Add a narrower seam only when a failure cannot be made deterministic through the public CLI.
- Follow the repository's existing case CLI integration-test prior art for fixture setup, command execution, output assertions, and post-command evidence inspection, without coupling the PRD to a particular source path.
- Prove successful preparation, privacy-safe preview, exact approval, durable recording, and receipt rendering for a complete three-part proposal.
- Prove that changing the reason, any evidence reference, the review appetite, expected revision, or other decision-bearing context after preview prevents the old approval from recording an event.
- Prove exact retry after success returns the established outcome and creates no second event; prove the same event identity with divergent content is refused and leaves state unchanged.
- Prove stale revision refusal after an intervening event, including exit status 3, bounded diagnostic output, and zero writes from the refused attempt.
- Prove public-only, private-only, and mixed-source privacy derivation. For private and mixed cases, assert that outputs and public state contain no private identities, paths, source, or evidence.
- Prove interruption before a durable write is safely repeatable and interruption after a durable write is recovered by idempotent retry.
- Prove incomplete proposals, unresolved evidence, invalid stewardship, unsafe privacy uncertainty, and injected write failures fail closed without partial records.
- For every governed refusal, assert all three parts of the contract in one test: refusal output, exit status 3, and write-free behavior.

## Out of Scope

- Changing or weakening the ordinary third-occurrence review-readiness rule.
- Automatic approval, automatic end-of-session capture, automatic refactoring, or automatic implementation delegation.
- Code-similarity detection, clone detection, or a general architecture audit.
- Implementing the accepted refactor inside the reuse-review capability.
- Scanning unmarked repositories or introducing a central portfolio repository.
- A hosted service, daemon, MCP server, sensor-plugin platform, or new shared lifecycle kernel.
- Publishing private repository identities, paths, source, evidence, or cross-repository membership into public state.
- Defining the missing evidence-reference CLI spelling in this lower-authority PRD before the active design is explicitly amended.
- New compatibility promises, storage schemas, or verification commands not already accepted by higher authority.

## Further Notes

- The foundational decision contract requires all three proposal parts and exact human acceptance. This PRD does not grant an override; each actual proposal must supply evidence references that bear its claim.
- The accepted per-event evidence decision remains the persistence authority, and the active version 0.1 design remains the implementation authority once its two-field CLI summary is corrected.
- The earlier illustrative TOML is intentionally not embedded: it came from a design discussion rather than a prototype, so the PRD's snippet exception does not apply.
- The narrowest authority change needed before publication is an accepted active-design amendment that adds evidence references to the direct-input shape and resolves their command-line contract. No foundational amendment is needed.
- Park this work if no real early-review case can provide all three required proposal parts, or if satisfying the workflow requires the out-of-scope platform machinery above. Falsify the design if the compiled CLI cannot prove exact approval, stale refusal, idempotent retry, private dominance, and write-free refusal at its public seam.
```
