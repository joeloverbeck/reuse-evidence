Proposed issue title: Governed early-review override for evidence cases

Testing seam: The already-ratified seam is the compiled public CLI; the PRD introduces no lower testing seam.

Exact issue body:

## Problem Statement

Maintainers sometimes have enough evidence to justify reviewing a possible reuse decision before the ordinary third-occurrence readiness threshold. Today, the local-first evidence workflow has no compiled, governed way to prepare that exception, show exactly what would be accepted, bind a human decision to the exact proposal, and record the result without weakening revision, identity, retry, or privacy guarantees.

This is not authority to extract early. It is a bounded way to ask for an early review. Waiting may itself impose coordination cost, but that claim is decision-bearing and must be supported by evidence references and a bounded review appetite. An unattended agent must not infer, omit, or silently rewrite any of those elements. A reviewer must be able to accept only the exact proposal presented, while an operator must be able to resume or safely retry interrupted work.

The immediate bottleneck is the mismatch between the foundational proposal contract and the active two-input CLI design. The foundational contract requires why waiting is worse, evidence references bearing that claim, and a bounded review appetite. The active design currently exposes direct inputs only for the reason and appetite. Until the active design is explicitly amended to carry evidence references too, an implementation issue cannot truthfully be published.

## Solution

Add a compiled early-review override flow to the local-first evidence CLI. The flow prepares and previews one exact proposal containing the reason waiting is worse, the supporting evidence references, and the bounded review appetite. Preview is deterministic and write-free. A later recording operation binds the human decision to that exact proposal, checks the expected case revision, uses a stable event identity, appends one immutable decision event, derives privacy from the referenced evidence, applies private dominance, and renders a privacy-safe receipt.

The accepted direct-input interaction remains the intended CLI style. Before implementation, however, the active design must be amended so that the direct interaction carries all three foundationally required proposal elements rather than only reason and review appetite. The implementation must not infer evidence references from ambient repository state or treat the human's earlier acceptance of the two-input shape as an amendment to the foundational contract.

The command must support safe interruption and idempotent resumption. Repeating the same event identity with the same decision-bearing content returns the already-recorded outcome without appending another event. Reusing an identity for different content, supplying a stale expected revision, presenting incomplete proposal material, or encountering any other governed refusal must leave case state unchanged and exit with status 3.

## User Stories

**Proposal preparation**

1. As a maintainer, I want an early-review proposal to include why waiting is worse, so that the exception has an explicit human rationale.
2. As an unattended implementation agent, I want proposal preparation to require evidence references bearing the rationale, so that I cannot manufacture unsupported review urgency.
3. As a reviewer, I want the proposal to state a bounded review appetite, so that accepting review does not become open-ended extraction authority.

**Preview**

4. As a maintainer, I want to preview the complete proposal before any write occurs, so that I can inspect the exact decision I may ask a human to accept.
5. As a reviewer, I want preview to render every decision-bearing field together, so that omissions or substitutions are visible before approval.
6. As an operator resuming interrupted work, I want the same inputs and case revision to reproduce the same preview, so that I can continue without reconstructing hidden state.

**Exact approval**

7. As a reviewer, I want my acceptance bound to the exact presented proposal, so that later changes require a new decision.
8. As a maintainer, I want any change to the rationale, evidence references, appetite, or case basis to invalidate prior approval, so that approval cannot drift across proposals.
9. As an unattended implementation agent, I want recording to prove that the approval corresponds to the exact previewed proposal, so that I cannot broaden a human decision.

**Expected revision**

10. As an operator, I want to record against an expected case revision, so that concurrent case changes cannot be silently overwritten.
11. As an unattended implementation agent, I want the CLI to refuse a stale expected revision before writing, so that I can safely refresh and re-evaluate the proposal.
12. As a reviewer, I want the accepted proposal tied to the case revision I reviewed, so that later evidence does not inherit an earlier approval automatically.

**Event identity**

13. As an operator, I want a stable event identity established before the recording attempt, so that retries refer to one logical decision event.
14. As an unattended implementation agent, I want event identity to be required at the public CLI boundary, so that retry safety does not depend on process memory.
15. As a reviewer, I want the receipt to identify the recorded event safely, so that the decision can be traced without exposing private evidence.

**Event recording**

16. As a maintainer, I want an accepted override recorded as an immutable event, so that the case history preserves what was decided.
17. As a reviewer, I want the event to preserve the exact proposal and human decision, so that later readers can distinguish review authority from extraction authority.
18. As an operator, I want recording to append rather than rewrite prior events, so that earlier case evidence remains auditable.

**Idempotent retry**

19. As an operator resuming after a lost response, I want to retry the same event identity and content safely, so that uncertainty does not create a duplicate decision.
20. As an unattended implementation agent, I want an identical retry to return the already-recorded result, so that recovery can be automated without a second mutation.
21. As a maintainer, I want reuse of an event identity with different content to be refused, so that identity collisions cannot corrupt case meaning.

**Stale revision refusal**

22. As an operator, I want a stale expected revision to produce a clear refusal, so that I know to reload the case before proceeding.
23. As an unattended implementation agent, I want stale-revision refusal to be write-free, so that a failed optimistic-concurrency attempt is safe to repeat after refresh.
24. As a reviewer, I want stale proposals to require renewed presentation and acceptance, so that my decision remains attached to current evidence.

**Privacy derivation**

25. As a private-repository steward, I want proposal privacy derived from the referenced evidence, so that callers cannot label sensitive material public by assertion.
26. As a maintainer, I want the preview to disclose the derived privacy class without exposing protected identities or paths, so that I can verify handling before approval.
27. As an unattended implementation agent, I want incomplete or ambiguous privacy inputs to fail closed, so that uncertainty cannot cause public disclosure.

**Private dominance**

28. As a private-repository steward, I want any private contributing evidence to make the combined proposal and decision private, so that public evidence cannot dilute stronger protection.
29. As a reviewer, I want private dominance applied consistently to previews, events, and receipts, so that one surface cannot leak what another protects.
30. As a maintainer, I want mixed public and private evidence to remain reviewable locally, so that privacy protection does not erase the decision trail.

**Receipt rendering**

31. As a maintainer, I want a concise receipt after successful recording, so that I can confirm the case revision and decision event that now exist.
32. As an unattended implementation agent, I want deterministic receipt rendering for both first success and identical retry, so that recovery does not create contradictory reports.
33. As a private-repository steward, I want receipts to omit private repository identities, paths, source, and evidence content, so that operational output is safe to retain.

**Interruption and resumption**

34. As an operator, I want interruption before commit to leave no event behind, so that restarting the flow begins from an unambiguous case state.
35. As an operator, I want interruption after commit but before receipt to be recoverable through an idempotent retry, so that I can learn the durable outcome safely.
36. As an unattended implementation agent, I want resumption to rely on case revision, proposal content, and event identity rather than hidden session state, so that a new process can continue correctly.

**Cross-repository stewardship**

37. As a private-repository steward, I want the flow to use only explicitly enrolled repositories, so that nearby unmarked repositories are never scanned or implicated.
38. As a maintainer, I want a proposal supported by evidence from multiple enrolled repositories to preserve each repository's stewardship boundary, so that review does not become evidence redistribution.
39. As a reviewer, I want cross-repository receipts to describe the decision without naming protected repositories, so that governance can be demonstrated without disclosure.

**Testing at the public CLI seam**

40. As a maintainer, I want acceptance tests to invoke the compiled public CLI, so that the proof covers the interface operators and agents actually use.
41. As an unattended implementation agent, I want success, retry, and refusal behavior verified through one stable public seam, so that internal refactors do not invalidate the contract.
42. As a reviewer, I want tests to assert observable output, exit status, and durable case state together, so that passing output alone cannot conceal an unsafe write.

**Unsafe failure**

43. As an operator, I want malformed or incomplete proposals refused before mutation, so that a correction does not require case repair.
44. As a maintainer, I want failed durable writes to leave no partially visible event, so that every observed event is complete.
45. As a private-repository steward, I want privacy uncertainty or unsafe rendering conditions to fail closed, so that availability pressure cannot override confidentiality.

**Refusal exit 3**

46. As an unattended implementation agent, I want every governed refusal to exit with status 3, so that I can distinguish an expected policy refusal from success.
47. As an operator, I want refusal output and exit status to agree while case state remains unchanged, so that scripted recovery cannot mistake a mutation for a refusal.
48. As a maintainer, I want successful first recording and successful identical retry to remain distinguishable from refusal, so that status handling is reliable.

**Documentation**

49. As a maintainer, I want documentation for preparation, preview, exact approval, and recording, so that I can follow the governed sequence without reading implementation code.
50. As an unattended implementation agent, I want documentation for expected revision, stable event identity, retry, and exit 3, so that automation uses the recovery contract correctly.
51. As a private-repository steward, I want privacy and cross-repository examples that use non-sensitive placeholders, so that the guidance demonstrates safe behavior without leaking real evidence.

## Implementation Decisions

- This issue is a coordinating parent for separately implementable work and is not itself an independently grabbable implementation unit.
- The feature extends the compiled, local-first evidence CLI. It does not create a service, daemon, background sensor, or central portfolio store.
- The prepared proposal has exactly three required semantic elements: why waiting is worse, one or more evidence references bearing that claim, and a bounded review appetite. Missing elements are a governed refusal.
- The ratified interaction style uses direct CLI inputs. The reason and review-appetite inputs remain direct. The exact direct mechanism for evidence references must be added by an explicit active-design amendment before implementation; evidence references must never be inferred from ambient repositories.
- Preview renders one canonical, complete proposal and performs no writes. The representation used to obtain approval and the representation validated during recording must carry the same decision-bearing content.
- Human approval applies only to the exact presented proposal. A change to its reason, evidence references, appetite, privacy derivation, or case revision requires a new preview and decision.
- Recording requires the expected case revision and checks it before mutation. A mismatch is a write-free governed refusal.
- The caller establishes a stable event identity before the first recording attempt and reuses it for recovery. Identity is part of the public command contract rather than transient process state.
- A successful decision is appended as one immutable per-event case record. Existing events are never rewritten to incorporate the override.
- Repeating an existing event identity with exactly matching decision-bearing content is idempotent and returns the existing recorded outcome. The same identity with different content is refused without writes.
- Privacy is derived from the referenced evidence and relevant repository stewardship. Callers cannot downgrade it. If any contributing evidence is private, private classification dominates the proposal, event, and receipt.
- Preview and receipt rendering must not expose private repository identities, paths, source, or evidence content. Private evidence remains locally available to authorized reviewers without being copied into public state.
- The receipt reports enough privacy-safe identity and revision information to distinguish a new recording, an identical retry, and a refusal.
- An interruption before durable commit leaves the case unchanged. An interruption after commit but before receipt is resolved by retrying the same event identity and content.
- Cross-repository evidence is limited to explicitly enrolled repositories and remains subject to each repository's stewardship boundary. The feature does not scan unmarked repositories or route private evidence into a public store.
- The override authorizes bounded human review only. It does not declare a shared responsibility, prove an abstraction, authorize extraction, or implement a refactor.
- Governed refusals use exit status 3 and must combine refusal output, that exit status, and write-free behavior. Success and unexpected operational failure remain distinct from governed refusal.
- Implementation work is delegated through bounded child issues. After implementation, the reuse lifecycle verifies the accepted result at the public CLI seam rather than duplicating the engineering workflow.

## Testing Decisions

- The highest and only required acceptance seam is the compiled public CLI. Tests exercise the same command surface used by maintainers, unattended agents, reviewers, and operators; internal helpers are not the acceptance contract.
- A good test asserts external behavior: exact relevant output, process exit status, and resulting durable case state. Tests do not couple to private implementation structure.
- Existing end-to-end case-command tests are the prior art for fixture setup, command invocation, durable-state inspection, and refusal assertions.
- Happy-path coverage prepares and previews a complete proposal, records an exact approval at the expected revision, appends one event, advances the case revision once, and renders a privacy-safe receipt.
- Proposal validation coverage independently omits the reason, evidence references, and bounded appetite and proves that each omission exits 3 with no write.
- Exact-approval coverage changes each decision-bearing field after preview and proves the earlier approval cannot record the changed proposal.
- Revision coverage records an intervening case event, attempts the stale override, and proves refusal output, exit 3, and byte-for-byte unchanged case state from immediately before the attempt.
- Event-identity coverage proves first recording, identical retry without a second event or revision advance, and same-identity/different-content refusal without writes.
- Interruption coverage exercises both pre-commit interruption and a lost post-commit receipt, then proves that resumption produces one durable event and a consistent receipt.
- Privacy coverage includes public-only, private-only, and mixed-source proposals. Mixed evidence must prove private dominance across preview, durable event, and receipt.
- Privacy tests use adversarial repository names, paths, and evidence text and assert that none appear in public output or public state.
- Cross-repository coverage proves that only enrolled repositories contribute, stewardship boundaries remain intact, and an adjacent unmarked repository is untouched.
- Unsafe-failure coverage induces malformed input, privacy uncertainty, stale revision, identity collision, and durable-write failure at the public boundary and checks that no partial event is observable.
- Documentation acceptance verifies that the described prepare, preview, approval, record, refusal, retry, and resumption flows match the compiled CLI behavior.

## Out of Scope

- Treating early review as automatic extraction authority or as proof that occurrences share one responsibility.
- Implementing any refactor, shared module, or downstream engineering change inside the reuse-review capability.
- Clone detection, generalized similarity scanning, or a general architecture audit.
- Automatic end-of-session capture, refactoring hooks, background capture, or clean/no-candidate evidence records.
- Scanning repositories that have not been explicitly enrolled.
- A hosted service, daemon, MCP server, sensor-plugin platform, or central portfolio repository.
- Weakening the foundational three-element proposal contract to preserve the current two-input design.
- Defining unratified persistence schemas, compatibility promises, or lower-level internal interfaces in this coordinating PRD.
- Publishing or implementing child work before the active-design mismatch is explicitly resolved.

## Further Notes

- **Human effect sought:** a maintainer can request a bounded early review when waiting is demonstrably worse, while reviewers and private-repository stewards retain exact-decision, concurrency, retry, and confidentiality guarantees.
- **Live bottleneck:** the active design's two direct inputs cannot carry the foundationally required evidence references.
- **Evidence bearing the proposal:** the foundational early-review decision contract, the accepted immutable per-event case model, the ratified public CLI testing seam, and the accepted capability coverage matrix from the preceding design discussion.
- **Narrowest sufficient scope:** amend the active design to add a direct evidence-reference input to the existing reason-and-appetite shape, then implement only preparation, preview, exact recording, recovery, privacy-safe receipt behavior, documentation, and public-CLI proof.
- **Explicitly excluded:** extraction, refactoring, automatic discovery, unmarked-repository scanning, hosted infrastructure, and general architecture analysis.
- **Authority conformance:** the draft preserves the foundational three-element proposal contract and immutable event model. The earlier acceptance of the two-input CLI shape is lower-level direction and does not amend that contract.
- **Falsify or park:** park the work if no real early-review case can provide evidence references for why waiting is worse, if a bounded appetite cannot be expressed without granting extraction authority, or if private cross-repository evidence cannot be represented without disclosure.
- No schema or type snippet is included because the illustrative TOML came from a design discussion rather than a prototype, and prose is sufficient to preserve the accepted semantic fields.
