# Version 0.1 Scope and Acceptance

**Status:** Active bounded design  
**Date:** 2026-08-09  
**Authority:** Subordinate to `docs/principles/` and accepted ADRs  
**Primary outcome:** A maintainer completes one real, private-safe reuse case from second occurrence through human decision and independent verification at acceptable routine burden.

This document authorizes the smallest implementation slice. It is not a speculative roadmap and does not make every named command or file shape permanent.

## 1. Live decision and bottleneck

The repository has already established that code reuse across agent-developed repositories is a real concern. The unresolved premise is whether a lightweight case lifecycle can improve decisions without becoming the bureaucracy or overfitted abstraction machine it is meant to prevent.

The first implementation must therefore prove:

- timely second-occurrence memory;
- ordinary third-occurrence review readiness;
- semantic human decision;
- safe private cross-repository evidence;
- external implementation handoff;
- independent verification;
- and write-free clean capture.

Detector sophistication, hosted collaboration, and broad legacy coverage do not answer this premise.

## 2. In scope

### Repository participation

- initialize a minimal versioned `reuse-evidence.toml` marker;
- generate or preserve stable repository and ecosystem identity;
- declare `public` or `private` visibility;
- discover marked repositories beneath configured local roots;
- report new, moved, unavailable, duplicate-ID, unsupported-version, and visibility-changed repositories.

### Durable case mechanics

- validate a minimal case event envelope;
- open a case against two evidenced independent occurrences;
- append later occurrences safely;
- derive watching and review-ready state;
- record a human-authorized early-review override;
- record an exact accepted decision by content identity and expected revision;
- record verification, park, close, and reopen outcomes;
- rebuild derived state from authoritative history;
- enforce private dominance and steward rules;
- keep local indexes disposable.

The exact event fields must be earned by this vertical slice. Do not pre-model every future action, sensor, language, or migration.

### Skill assets

Provide repository-installed skills for:

- `reuse-evidence-capture`;
- `reuse-evidence-discover`;
- `reuse-evidence-review`;
- `reuse-evidence-status`.

The installer writes real files under `.claude/skills/` and symlinks under `.agents/skills/`, refuses atomically on conflicting local modifications, and reports exact consequences.

### Capture

- manual invocation after material work;
- bounded diff/task/source/test inspection;
- current-repository and enrolled-portfolio comparison as needed;
- fixed no-candidate terminal result with no write;
- exact preview before opening or appending a case;
- no transcript parser.

### Discovery

- manually invoked and read-only until a human selects a candidate;
- bounded by repository, selected set, or portfolio;
- limited to repeated responsibility or wrong-abstraction pressure;
- may use optional external sensors;
- produces temporary candidate output rather than a committed audit report.

### Review and decision

- identity and independence assessment;
- invariant and variation analysis;
- narrowest-scope comparison;
- existing dependency research when the decision requires it;
- public/private consequence;
- exact proposed decision;
- bounded implementation brief after human acceptance.

### Verification

- compare the accepted decision with the actual implementation result;
- verify named consumer behavior through repository-defined commands or artifacts;
- ensure migrations or accepted exceptions are complete;
- close, park, or reopen without rewriting history.

### Language proof

- Rust/Cargo as the strongest operational path;
- TypeScript/JavaScript repository enrollment and clean capture;
- no Cargo-only requirement in case evidence.

## 3. Out of scope

Version 0.1 must not include:

- a built-in exact, structural, fuzzy, or semantic clone detector;
- required embeddings, GPU support, external model APIs, or remote source upload;
- automatic Stop, post-commit, or CI capture;
- automatic refactoring;
- an integrated extraction implementation skill;
- a general architecture audit;
- a DRY or portfolio health score;
- CI failure on unreviewed candidates;
- a hosted service, account system, telemetry, daemon, or background watcher;
- an MCP server;
- a generalized sensor plugin framework;
- a central portfolio repository or synchronized per-participant case copies;
- ordinary steward transfer;
- a public package recommendation service;
- a product-line framework for games, worlds, stories, or agent tools;
- a shared event-lifecycle crate extracted with `skill-evidence`;
- a public host-mounting API that lets every consumer rename and embed the command tree;
- migration of every legacy duplicate in the portfolio;
- or a speculative multi-release roadmap.

## 4. Smallest coherent vertical slice

The first risk-bearing slice should demonstrate one case with a synthetic or sanitized fixture corpus before expanding to broad repository scans:

1. initialize three marked repositories with mixed visibility fixtures;
2. record two independent occurrences in a valid private steward;
3. prove the case derives `watching`;
4. append a third independent occurrence and derive `review-ready`;
5. present a semantic decision proposal;
6. record exact human acceptance against expected revision;
7. produce an implementation brief;
8. simulate or perform external implementation;
9. verify named consumer contracts;
10. close the case;
11. rebuild all derived state from the event stream;
12. prove that private evidence cannot be written into a public steward;
13. prove that a clean capture creates no event or report.

The slice should be interrupted between steps and resumed from durable state to prove no transcript reconstruction, repeated decision, stale application, or duplicated effect is required.

## 5. Real acceptance cases

After the synthetic or sanitized slice passes, version 0.1 requires bounded dogfooding.

### A. Historical extraction geometry

Reproduce the evidence shape that led to `skill-evidence`:

- initial local implementation;
- second independent consumer;
- third consumer;
- minor variation;
- decision to create a shared public Rust crate;
- consumer migration.

Private source need not enter the public fixture corpus. The public tests may use synthetic repositories while the maintainer performs a private local replay against recoverable Git evidence.

### B. Live private Rust product-repository case

In a maintainer-selected private Rust repository, capture one real repeated responsibility among independently developed products, engine consumers, analysis consumers, or workflow edges. The public repository must not record the private repository identity or confidential case evidence.

A successful result may be intentional locality, watching, extraction, generation, an existing dependency, or rejection of the supposed commonality. The system is not required to manufacture a shared framework.

### C. Live cross-repository case

Run bounded discovery across enrolled Rust repositories and select one genuine candidate involving at least two repositories. The case must exercise steward and private-dominance behavior. It need not end in extraction before publication.

### D. TypeScript proof in `continuity-loom`

Enroll the TypeScript/JavaScript workspace and complete a clean capture that:

- finds the npm workspace without requiring Cargo;
- writes no case event when no qualifying pressure exists;
- and demonstrates language-neutral repository and evidence semantics.

### E. `skill-evidence` adoption

Install and operate `reuse-evidence` in the public `skill-evidence` repository without creating a production dependency or prematurely extracting a shared lifecycle kernel.

## 6. Operational acceptance

Version 0.1 is not fit if routine use becomes a report-writing ceremony.

Acceptance requires:

- a clean capture to need one explicit invocation;
- no committed artifact for no-candidate results;
- no mandatory detector or model setup;
- case status understandable from inspectable repository state;
- privacy consequences visible before writes;
- interrupted work resumable without transcript recovery;
- and the maintainer willing to repeat the workflow after real coding sessions.

Manual testing requests must name the decision affected, why automation or a smaller proxy is insufficient, expected burden, and stopping condition.

## 7. Stop and reframe conditions

Stop version 0.1 expansion and revisit the design if any of these occurs:

- opening a second-occurrence case requires so much semantic form-filling that the maintainer avoids capture;
- the event model must encode detector internals to function;
- private cross-repository evidence cannot be handled without copying or centralizing source;
- review repeatedly duplicates ordinary architecture or implementation skills;
- clean capture creates durable noise;
- TypeScript participation forces Cargo concepts into authoritative state;
- the system routinely recommends extraction from similarity alone;
- or verification cannot distinguish an implemented migration from a correct reuse decision.

Exhausting the bounded appetite stops and reframes the work by default. Do not extend the design merely to salvage sunk implementation.

## 8. Publication threshold

The crate may be published early once the smallest coherent lifecycle, privacy refusal, durable resumption, installer safety, and initial dogfood evidence are honest and passing.

Publication does not imply 1.0 stability, broad language support, public adoption, hosted services, or support commitments. The README must describe actual implemented behavior and known limits rather than the full intended design.
